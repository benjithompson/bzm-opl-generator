# bzm-opl — BlazeMeter private location agent (Helm)

Installs a BlazeMeter private location agent (crane) on Kubernetes or
OpenShift. It supports **performance testing**, which needs no extra settings,
and **service virtualization**, which needs `sv.ingress` (see below).

The chart renders the same objects as the generated `kubectl` manifests. A
bundle generated by `bzm-opl-gen generate --format helm` includes this chart
plus a values file (`bzm-opl-values.yaml`) filled in from your account; that
is the easiest way to install. `helm show values ./helm` documents every value.

## Install

`harborId`, `shipId` and `authToken` are required:

```
helm install crane ./helm -n blazemeter --create-namespace \
  --set harborId=<harbor-id> \
  --set shipId=<ship-id> \
  --set-string authToken=<token>
```

The ids are on the private location's page in BlazeMeter (Settings → Private
Locations); the token is the agent's. To keep the token out of values files,
create the Secret yourself:

```
kubectl -n blazemeter create secret generic bzm-auth --from-literal=AUTH_TOKEN=<token>
helm install crane ./helm -n blazemeter \
  --set harborId=<harbor-id> --set shipId=<ship-id> --set existingSecret=bzm-auth
```

Then confirm the agent shows **online** in BlazeMeter under Settings → Private
Locations.

## Common configurations

**OpenShift** — `--set platform=openshift`. The restricted-v2 SCC assigns the
UID, so `runAsUser` is not set.

**Private registry** — set `privateRegistry` and `imageOverrides` together (the
chart refuses one without the other). Generate both with bzm-opl-gen, and push
the images with the mirror script it writes:

```
bzm-opl-gen generate --api-key api-key.json --harbor-id <harbor-id> \
    --format helm --private-registry registry.example.com/blazemeter --out out
./out/bzm-opl-image-mirror.sh
```

**Corporate CA** — pick one mode:

```
# a ConfigMap your platform team manages (trust-manager, etc.)
--set caBundle.mode=existing --set caBundle.existingConfigMap=trust-bundle

# your own PEM
--set caBundle.mode=inline --set-file caBundle.pem=/path/to/ca.crt

# OpenShift injects the cluster-wide bundle
--set caBundle.mode=openshiftInject --set platform=openshift
```

**Proxy** — `--set proxy.enabled=true --set-string proxy.http=http://px:3128`.
Put credentials in the URL (`http://user:pass@host:port`); such a URL is stored
in the Secret rather than the ConfigMap.

> JMeter ignores `HTTP(S)_PROXY` for test traffic, so configure the proxy in the
> test itself as well. Results upload through the agent's proxy settings.

**Service virtualization** — `sv.ingress` chooses how crane publishes each
virtual service:

```
--set sv.ingress=nginx \
--set sv.subdomain=mocks.example.com \
--set sv.tlsSecret=wildcard-mocks
```

| `sv.ingress` | crane publishes | works with `serviceType: NODEPORT` | reads `sv.tlsSecret` |
|---|---|---|---|
| `nginx` | an Ingress (`networking.k8s.io`) | yes | yes |
| `istio` | a Gateway + VirtualService (`networking.istio.io`) | no | no |
| `contour` | an HTTPProxy (`projectcontour.io`) | no | yes |
| `openshift` | a Route (`route.openshift.io`) | yes | no |

The Role grants only the chosen backend's API group. You provide:

- **A wildcard DNS record** for `*.<sv.subdomain>` pointing at your ingress
  controller. Endpoints are `<virtual-service>-<port>-<namespace>.<sv.subdomain>`.
- **The TLS Secret** named by `sv.tlsSecret`, in the agent's namespace. The name
  is always required; for nginx and contour the Secret must exist and cover the
  wildcard domain, or endpoints are served with the controller's default
  certificate.

Leave `sv.ingress` empty for a performance-only agent. Virtual services deployed
to a location without it stall at `WAITING_FOR_DOMAIN`.

## Engine sizing

Crane itself is small; engines use the capacity. Each concurrent engine needs
2 CPU + 8Gi RAM by default, plus about 60GB of disk (40GB of it `/tmp`).
`bzm-opl-gen doctor` checks a cluster against these figures.

`engine.cpuLimit` / `engine.memoryLimit` set the engine pod's **limits**, and
`engine.cpuRequest` / `engine.memoryRequestMi` its **requests** (empty: equal to
the limits; memory in MiB). The scheduler places pods by requests, so keeping
them equal to the limits stops engines sharing a node and skewing results. A
location's `overrideCPU` / `overrideMemory`, if set in BlazeMeter, replace the
requests.

An existing LimitRange in the namespace must allow both the engine size and
crane's own limits (1 CPU / 2Gi), or the pod is rejected at admission.

## Upgrades and auto-update

`autoUpdate` is off by default. `helm upgrade` then works normally, and a
configuration-only change still restarts the pod (the Deployment carries
checksums of the ConfigMap and Secret). Keep the agent current by bumping
`image.tag` and upgrading; an agent that falls far behind loses support.

With `autoUpdate: true`, crane updates its own Deployment and takes ownership of
fields Helm manages, so a later `helm upgrade` fails with a field-ownership
conflict (`--force-conflicts` does not resolve it). Changes then require
`helm uninstall` + `helm install`.

## Cluster RBAC

`clusterRbac` (off by default) grants read access to nodes. Crane uses it only
for capacity reporting; without it, crane logs a `forbidden: nodes` warning and
works normally, with either `serviceType`. Cluster-scoped names include the
namespace (`cluster-role-binding-crane-<ns>`), so locations in different
namespaces do not collide.

## Names

Objects use fixed names that match the generated manifests — Deployment
`crane`, `blazemeter-configmap`, `blazemeter-secret`, `role-crane` — so the
`-l role=role-crane` selectors in BlazeMeter's documentation work.
`fullnameOverride` makes them release-specific.

`harbor_id` and `ship_id` are part of the Deployment's selector, which is
immutable: pointing an install at a different agent needs `helm uninstall` +
`helm install`.

## What it renders

| Object | When |
|---|---|
| ServiceAccount `serviceAccount.name` (default `crane`) | `serviceAccount.create` (default on) |
| ConfigMap `blazemeter-configmap` | always |
| Secret `blazemeter-secret` | `useSecret` and no `existingSecret` |
| Role/RoleBinding `role-crane` | always |
| Deployment `crane` | always |
| ConfigMap `blazemeter-cacerts` | `caBundle.mode` inline or openshiftInject |
| ClusterRole/Binding | `clusterRbac` |

Crane creates the service virtualization ingress objects itself at run time.

With `serviceAccount.create: false`, `serviceAccount.name` is required and must
name an existing account; the chart never falls back to the namespace's
`default` account.

## Check a render before installing

```
helm lint ./helm --set harborId=h --set shipId=s --set-string authToken=t
helm template crane ./helm -n blazemeter \
  --set harborId=h --set shipId=s --set-string authToken=t
```

The chart validates its values and fails the render with a message naming the
fix for combinations that would otherwise deploy an agent that cannot work.
